# ViewModel Architecture

Guidance for standardizing ViewModels with shared loading/error state and consistent QML bindings.

## BaseViewModel (C++)
- Inherits `QAbstractListModel`; exposes `isLoading`, `hasError`, `errorMessage` (read-only, QML-visible).
- Signals: `isLoadingChanged`, `hasErrorChanged`, `errorMessageChanged`.
- Standard retry hook: `Q_INVOKABLE reload()` (no-op by default; override to call your load/refresh entry point).
- Helpers:
  - `setLoading(bool)` to flip busy state (emits change once).
  - `setError(QString)` / `clearError()` to manage error flags and text.
  - `emitModelReset(fn)` wraps `beginResetModel`/`endResetModel` around a mutator.
  - `mapNetworkError(endpoint, error)` maps common service failures to user-friendly strings.

## Migration guidance
- Derive list-style ViewModels from `BaseViewModel` (e.g., `LibraryViewModel`, `SeriesDetailsViewModel`).
- Remove bespoke `isLoading`/`errorMessage` flags and use the base helpers.
- Route network callbacks through `setError(mapNetworkError(...))` and clear errors before new loads.
- Use `emitModelReset([&]{ ... })` when replacing model contents; use `dataChanged` for partial updates.
- Keep role definitions and business logic localized; only loading/error plumbing moves to the base.

## QML usage
- Bind spinners/toasts to `isLoading`/`hasError`/`errorMessage` without custom glue per ViewModel.
- After model reloads that affect focusable delegates, use `Qt.callLater` to restore focus per `docs/developer_notes.md`.
- Retry pattern (with shared `StateMessage.qml`):
```qml
Column {
    BusyIndicator { running: model.isLoading; visible: running }
    StateMessage {
        visible: model.hasError
        kind: "error"
        message: model.errorMessage
        actionText: qsTr("Retry")
        onActionTriggered: model.reload()   // BaseViewModel::reload()
    }
}
```

## Current migrations
- `LibraryViewModel` now inherits `BaseViewModel`; loading/error wiring is centralized while pagination, caching, and signals (`loadComplete`, `loadMoreComplete`) remain intact. It consumes connection- and request-aware canonical `LibraryService` results, exposes canonical camelCase `modelData`, resolves posters from `ArtworkRef` maps, compares complete canonical objects during SWR, and rejects provider wire-shaped disk-cache rows. When refreshed identities/order are stable, changed rows are replaced in place with role-specific `dataChanged` notifications; structural changes still reset the model.
- `LibraryViewModel.loadCombinedLibraries(libraryIds, collectionType, limit)` shows several libraries of one kind as one list ("All Movies"). It pages each library with the current sort and filters (recursive, flat, library order treated as title) and merges the pages with `CombinedLibraryCursor` (`Bloom::Models`), which releases an item only once every library still holding items has one buffered, so the merged order never changes as pages arrive. `loadMore`, reload and filter options (the union of each library's genres, tags and studios) work on the combined list; combined pages skip the SWR cache. A failed library is skipped; all failing is an error. `CombinedLibraryTest` covers the merge.
- `LibraryViewModel` owns per-library root search, sort, and broad filters. The UI currently exposes stable sort fields (library order, title, release date, date added, rating, year, random) and hides watched filtering, watched/runtime sort controls, and year-range inputs until those interactions are reliable. Series details, seasons, movie details, and playback-return contexts stay outside this root-library filter state.
- `LibraryViewModel.letterIndex` is where each letter starts in the whole title-ordered library (`{letter, count, position}` in list order). In title order, `loadLibrary` of a paged library asks `LibraryService::getLibraryLetters` for the index of the same query (filters and order); the answer is kept per dataset in memory for 15 minutes (building it can mean reading the whole list, on Jellyfin) and shown at once on a return; a background refresh that finds the first page changed marks it stale and reads it again while it stays shown. Other sorts, unpaged loads (series children), combined pages and a failed or unsupported read leave it empty, and the rail falls back to the letters of the loaded rows. Only the answer for the current dataset is applied. `letterAtPosition(position)` reads the index's runs, which the rail uses for the focused card's letter.
- `jumpToLetter(letter)` and `seekToPosition(position)` make a row available and emit `positionReady(position)` once it is loaded (at once when it already is). A position past the loaded rows grows the model with placeholder rows (`modelData.bloomPlaceholder`) up to one window after it and reads that window (100 rows) starting at the position: Silo's `seek` with the window cursor, Jellyfin's `StartIndex`. `ensureLoaded(index)` reads the window holding a placeholder row when its card is shown, upward from it above a jump and downward below; windows in flight are not read twice, and at most two such reads run at once: while Down is held through placeholders, only the newest row asked for is read when one answers, and rows scrolled past stay placeholders until shown again. A seek's own window is never held back. Window pages replace placeholders only, a page that was in flight when placeholders appeared fills its own rows, a shorter list drops placeholders past its new end, and a failed window leaves its placeholders to be read again; when a seek waited on it, `seekFailed(position, error)` lets `LibraryScreen` say so, and the same jump retries. A seek asked for while the first page loads runs once it is in. Window pages are not cached (the cache keeps the contiguous prefix); a jump drops a pending background refresh, which would reset the model under it. On a stale cache the refresh is registered before the cached rows are published, so a seek started from `loadComplete` cancels it too. `loadedCount` counts rows with a title (no placeholders) for the header. `LibraryScreen` focuses the row on `positionReady`, and a return to a title past the loaded pages (more than 800 rows in) seeks back to it instead of reading every page before it, restoring the grid's scroll position. `LibraryViewModelCanonicalTest` covers the index ownership, jumps, windows, pages in flight, a shrunk list, failures, the return seek over a stale cache, a seek during the first load, and the placeholder read limit.
- `LibraryViewModel.supportedSorts` and `supportedFilters` hold the canonical sorts and filters the active connection serves (`ProviderLibraryQueryCapabilities`, from `ICatalogProvider::libraryQueryCapabilities` through `LibraryService::libraryQueryCapabilities`). Jellyfin serves every one; Silo has no `random` sort and no `tags` or `seriesStatus` filter. The view model then narrows them to the open library: `recentlyUpdated` and `seriesStatus` only in series libraries, `resolution` only in movie libraries, and on combined pages only the sorts `CombinedLibraryCursor::canMerge` can merge (no `recentlyUpdated`, since no card field carries a series' newest-episode date). It reads them on every `loadViews`, `loadLibrary` and `loadCombinedLibraries`, after taking the new library kind and before it builds a query. A sort or filter that the connection or library kind does not serve, such as Random kept from a Jellyfin library, falls back to library order or no filter, and `setSortBy`, `toggleTag`, `setAddedSinceFilter`, `setSeriesStatusFilter` and `setResolutionFilter` refuse unsupported values. `seriesStatusFilter` is `any`, `continuing` or `ended`; `resolutionFilter` is `any`, `4k` or `hd` (HD and up). Both count toward `activeFilterCount`, reset with `clearFilters`, and reach `LibraryItemQuery` as empty or canonical values that are part of the dataset key. Choosing `datePlayed` or `recentlyUpdated` with no order set sets `descending`. `LibraryScreen` builds the sort menu and the Genres/Tags/Studios tabs from these lists and hides the "Added since", series status and resolution menus when their filter is missing, so focus never reaches a hidden control. Every provider serves the favorite and rating filters, which stay visible. Filter and sort state is not persisted; opening a library clears it (`clearQuery`).
- Library loading separates dataset identity from request identity. `LibraryItemQuery::datasetKey()` contains connection-independent query semantics (parent, search, filters, sort, item types, and recursion) but excludes offset, limit, and field shape. Each operation gets a generation-scoped request token plus a typed load kind (`Views`, `Initial`, `LoadMore`, `BackgroundRefresh`, or `FilterOptions`). Only the request that currently owns a state flag may clear it or publish results/errors; late success and failure signals are rejected. Connection/profile changes start a new generation.
- Initial pages, later pages, and SWR refreshes share one connection-scoped cache snapshot. Empty snapshots are valid cache entries, while snapshots containing undecodable rows are rejected. Pagination replaces a requested position range only when its preceding range is contiguous; an isolated nonzero-offset result is never reused as page zero. A successful first-page SWR response invalidates unverified later pages because insertions, deletions, or sorting changes can shift page boundaries; a provider-level not-modified response retains the full snapshot. The process-wide memory tier is bounded to 48 datasets or approximately 32 MiB with LRU eviction. Persisted SQLite caches remain isolated by connection scope.
- Filter facets are loaded per library through request-aware `LibraryService` operations and cached separately from item result slices. Recursive filtered queries use collection-type item narrowing (`Movie` for movie libraries, `Series` for TV libraries, both for mixed/unknown libraries). A failed or superseded facet request cannot leave `filterOptionsLoading` active.
- `SeriesDetailsViewModel` inherits `BaseViewModel` for standardized loading/error properties and consumes only connection-aware canonical series/item-list/next-episode/similar-item/focused-item/chapter signals. Nested `SeasonsModel`/`EpisodesModel` expose canonical camelCase roles, including `durationMs`, `positionMs`, special-placement fields, and connection-scoped artwork URLs.
- `SeriesDetailsViewModel` has the same watchlist API as `MovieDetailsViewModel` (`watchlistSupported`, `inWatchlist`, `toggleWatchlist()`, `watchlistUpdateFailed`) for the series.
- `SeriesDetailsViewModel` and the QML series entry points load children through `LibraryService::getSeasons` and `getSeasonEpisodes`, never untyped `getItems(parentId)`. Silo treats an untyped parent as a library ID.
- `SeriesDetailsViewModel` owns canonical stale-while-revalidate caches for series metadata, seasons, episodes, and recommendations. Wire-shaped payloads are rejected. Request-start `connectionId` and focused-episode ownership tokens prevent late responses from another source or episode from changing the active view.
- Focused-episode chapters use canonical `name`, `startMs`, and `ArtworkRef` data, with a small in-memory per-episode cache for quick return navigation. `SeriesSeasonEpisodeView.qml` and the player request boundary keep playback and chapter timing in milliseconds.

## MovieDetailsViewModel
ViewModel for the series-style movie details screen.

### Purpose
Acts as the data source for `MovieDetailsView.qml`. It aggregates canonical movie metadata, playback progress, chapters, cast, similar-library recommendations, and external ratings from MDBList (IMDb, TMDB, Rotten Tomatoes, etc.) plus AniList when available. It consumes `LibraryService::canonicalItemLoaded` / `canonicalSimilarItemsLoaded` only; raw Jellyfin DTO signals remain for unmigrated flows.

### Public API
- **Key Properties**:
  - `title`, `overview`, `logoUrl`, `posterUrl`, `backdropUrl`: UI-ready metadata and artwork.
  - `officialRating`, `durationMs`, `communityRating`, `premiereDate`, `genres`: movie metadata used by the hero chips and synopsis area.
  - `isWatched`, `positionMs`: sync with canonical user state and drive `Play` vs `Resume` UI.
  - `watchlistSupported`, `inWatchlist`: the watchlist action, shown only when the active provider has a watchlist (`LibraryService::supportsWatchlist`, Silo). `inWatchlist` comes from canonical `inWatchlist`.
  - `people`: cast/crew entries used by the lower cast shelf (canonical person maps).
  - `chapters`, `chaptersLoading`: normalized movie chapter cards plus the rail loading state.
  - `similarItems`, `similarItemsLoading`: recommendation shelf data and loading state for similar titles (`itemId`, `primaryArtwork`, camelCase fields).
  - `extras`, `trailer`: the movie's canonical local extras and the one Play Trailer starts (empty without a trailer or teaser). Both change with `extrasChanged`. A detail that carries `extras` (Silo) supplies them; otherwise the view model calls `LibraryService::getItemExtras` (one request in flight per movie and connection) and applies only the matching answer. `ItemExtrasState` (`src/viewmodels/ItemExtrasState.h`) holds this logic and a small in-memory cache: a return visit shows the cached shelf at once and refreshes it in the background. A partial answer (one of Jellyfin's two reads failed) is shown but never cached. `extrasLoading` (`extrasLoadingChanged`) is true while a requested answer is outstanding, so a page restoring focus to the Extras shelf waits for it instead of falling back. `SeriesDetailsViewModel` exposes the same two properties for the series.
  - `mdbListRatings`: `QVariantMap` containing normalized external ratings, including AniList when merged in.
  - `userRating`: the viewer's own rating of the movie, a `UserRatingState` (see [user ratings](#user-ratings)). `SeriesDetailsViewModel` has the same property for the series.
- **Methods**:
  - `loadMovieDetails(QString movieId)`: hydrates from cache when possible, then refreshes metadata and similar items from the library service.
  - `reload()`: retries the active movie load for error/retry flows.
  - `markAsWatched()` / `markAsUnwatched()`: sync played status to the server.
  - `toggleWatchlist()`: adds or removes the movie. `inWatchlist` changes at once; while the write is in flight further presses and refreshed details are ignored. A refusal restores the previous state and emits `watchlistUpdateFailed(message)` for a toast. A confirmed change updates the details cache.
  - `clear(bool preserveArtwork)`: resets state. Set `preserveArtwork=true` to keep artwork visible during transitions.
  - `loadMovieChapters(QString movieId)` / `clearMovieChapters()`: load or reset the active movie chapter rail.
- **Signals**:
  - `movieLoaded()`: metadata is ready for display.
  - `loadError(QString error)`: standardized error notification. Only a failed movie read (`getItem`) fails a load; errors of other `LibraryService` reads, such as Home's background rows, are not the page's.
  - `peopleChanged()`, `chaptersChanged()`, `chaptersLoadingChanged()`, `similarItemsChanged()`, `similarItemsLoadingChanged()`: update the lower metadata shelves.

### Integration
- **Services**: Retrieves `LibraryService` via `ServiceLocator` for movie details, user-data updates, and similar-item requests.
- **Network**: Uses an internal `QNetworkAccessManager` for MDBList and Wikidata/AniList lookups through `ExternalRatingsHelper`. Each request has a 15 s transfer timeout, and error text is passed through `redactNetworkLogText` because the MDBList request URL carries the API key.
- **Config**: Reads `ConfigManager` for API keys and cache storage paths.

### Lifecycle & Side Effects
- **Caching**: Uses separate in-memory and disk caches for canonical movie details and similar items. Disk cache resides under `<configDir>/cache/connections/<scope>/movies/` with `*_details_canonical.json` / `*_similar_items_canonical.json` filenames and a 1-hour TTL; wire-shaped caches are rejected. Movie chapters keep a small in-memory per-movie cache so returning to a movie does not immediately re-show loading skeletons.
- **Rating Fetching**: Automatically triggers external rating lookups after metadata loads when provider IDs (IMDb/TMDB) are present.
- **Recommendation Fetching**: Requests similar items after details load, while still allowing cached empty recommendation results to short-circuit redundant network fetches.
- **State Cleanup**: `clear()` should be called when navigating away from the view to prevent stale shelves or metadata from lingering.
- **Stacked detail pages**: `MovieDetailsViewModel` and `SeriesDetailsViewModel` are app-wide, but a person page can stack a second details page over the first (movie A → cast → person → movie B). Each details view therefore acts on the shared model only while it holds the view's own `movieId`/`seriesId` (`sharedModelCurrent`): load handlers, focus timers and toasts of a hidden page do nothing, and Mark Watched, Watchlist, Favorite and Play, which take no ID, are ignored otherwise. When a `LibraryScreen` becomes the current page again, `reloadSharedDetails()` reloads its own title if the model holds another (the detail cache serves it), and focus returns to the cast card that opened the person once the cast is back. The season view also puts back the season and episode that were on screen, with focus on that episode.

## HomeSectionsViewModel
The rows a Silo profile curates for its Home page, which `HomeScreen.qml` shows below its own shelves (see [provider compatibility](provider-compatibility.md#catalog-and-conditional-requests) for which rows), and for Jellyfin the Favorites row (for providers without a watchlist) followed by personalised movie recommendation rows (see [Jellyfin Home](provider-compatibility.md#jellyfin-home)).

- **Model**: one list row per server row, in layout order, with roles `sectionId`, `title`, and `items` (canonical camelCase item maps). `LibraryService::getHomeSections` chooses the rows and maps the items; the model owns only their lifecycle.
- **Libraries**: Home passes the libraries it shows (the space's visible ones), in its order, to `setLibraries(views)` whenever its views load and when the library order changes in Settings. The model keeps the IDs of the movie libraries among them (`LibraryKinds`), for the connection active at that moment, and every refresh passes them to `getHomeSections(movieLibraryIds, reloadRecommendations)`; a refresh under another connection passes none. `clear()` forgets them.
- **Watch Tonight row**: for providers with `ProviderCapability::WatchTonight` (Silo) and with `ConfigManager::homeWatchTonightEnabled` on, `getHomeSections` reads `ProviderCatalogOperation::WatchTonight` (`listWatchTonightCards`, discover mode, 20 cards) beside the layout. The row (`LibraryService::WatchTonightRowId`, "Watch Tonight") comes first, before the Watchlist row and the profile's rows, so it follows Bloom's own shelves. The layout never waits for it: the rows publish as soon as the layout is read, with the Watch Tonight row LibraryService already knows for the connection and user, and an answer that lands later publishes the rows again with `canonicalHomeSectionsUpdated`, which the model applies in place (the row is inserted above the others, `rowsInserted`). It is read once per connection and user and again only on `refresh(true)` (a new Home, after playback); favorite, watchlist and setting refreshes reuse it. An `is_cold` answer (a generic fallback, not the profile's taste) or no movie, series or episode cards remove the row; a failed read keeps the row known before (none on the first read). A failed layout read waits for a Watch Tonight read in flight and still shows its row; the refresh fails only when both fail and no row is known. Turning the setting off calls `removeWatchTonightRow()` first, which removes the row at once (`rowsRemoved`); turning it on refreshes. Merged spaces show none, like the curated rows. No exclusions or paging state are kept: the row is the first page, read again with the other rows.
- **Recommendation rows**: for providers with `ProviderCapability::MovieRecommendations` (Jellyfin) and with `ConfigManager::homeRecommendationsEnabled` on, `getHomeSections` reads `ProviderCatalogOperation::MovieRecommendations` once per movie library, side by side with the Favorites read, and publishes once all have answered.
  - *Shown libraries only*: Jellyfin's `ParentId` only picks the seed titles; similar titles and people's films come from every library the user may open, including ones the space hides. Once the libraries answer, one batched `ProviderCatalogOperation::LibraryMembership` read per shown movie library (`GET /Items` with `ParentId` and at most `MembershipBatchSize` = 60 `Ids`) finds which recommended items lie in a shown library, and every other item is dropped. When a membership read fails, only items an earlier read found in the same libraries are kept.
  - *Server version*: `ProviderCatalogOperation::ServerInfo` (`GET /System/Info/Public`) is read once per connection. `HomeRecommendations::similarRowsWork` keeps the "Because you watched" and "More like" categories only on Jellyfin 10.10 and older or 12.0 and newer: 10.11 builds them without their baseline, so they all list the same movies. A failed version read hides them and is asked again next time. A "similar to" category whose items equal those of a category with another title is also dropped. "Directed by" and "Starring" rows always stay.
  - *Reuse*: the server picks its seed titles at random, so each read reshuffles the rows. The answer is kept per connection, user and set of shown movie libraries for `CacheLifetimeMs` (45 minutes). Only `refresh(true)` reads again: a new Home (the first views load), after playback stops, and when the setting is turned on. Other refreshes (a favorite or watchlist change, returning to Home, a library reorder) re-read the Favorites row only and rebuild the recommendation rows from the kept read, in the current library order. Another set of shown libraries reads again. A read with a failed library, membership or version read is shown but not reused.
  - *Failures*: a library whose read fails shows the categories it answered last, if any.
  - *Building rows*: `HomeRecommendations::rows` (`src/models/HomeRecommendations.*`, `Bloom::Models`) turns the categories into rows in library order and then the server's order: the title comes from the reason and the baseline name ("Because you watched %1", "More like %1", "Directed by %1", "Starring %1"; a category with an unknown reason or no baseline is dropped), only movie cards are kept, each once and at most 15 per row, and a category with the same reason and baseline as an earlier one (the same title read from another library) adds its new cards to that row instead of repeating it. Rows without cards are dropped and at most 8 rows are kept. Section IDs are `bloom:recommendations:<type>:<baseline>`, so a refresh with the same rows updates them in place. They come after the Favorites row.
- **Loading and errors**: `refresh()` loads in the background with `isLoading`. A failure sets `hasError`/`errorMessage` and keeps the rows already shown; Home shows no error for these rows, like its other shelves. `reload()` retries. A failed Favorites or recommendation read leaves the rows of the other reads; the refresh fails only when every read failed and no other row is left.
- **Ownership**: only the answer to the newest request for the active connection is applied. Refreshing under another connection drops the old rows first. `clear()` drops the rows and the pending request; Home calls it for a new Home and in merged spaces, which have no curated rows, no Favorites row and no recommendation rows. Every `getHomeSections` call starts a new generation; answers of an older one, or for a connection or profile that is no longer active, are dropped.
- **Updates**: a refresh updates rows in place: rows it keeps change their titles and items (`dataChanged`), new rows are inserted (`rowsInserted`) and gone rows removed (`rowsRemoved`), so the other shelves keep their delegates and focus; Home scrolls the focused shelf back into view, and a removed focused row hands focus to the row now in its place. Only a reorder of kept rows resets the model. Turning the recommendation setting off calls `removeRecommendationRows()` first, which removes the rows whose section ID starts with `HomeRecommendations::SectionIdPrefix` at once (`rowsRemoved`, so the other rows keep their delegates), whatever the following refresh answers. A confirmed watchlist change refreshes rows loaded or loading for the live connection (a read in flight may predate the change), and so does a confirmed favorite change when the provider has the Favorites row (`LibraryService::supportsHomeFavoritesRow`); Silo's rows ignore favorites.
- **Focus**: Home saves a focused row as `serverRow:<sectionId>` with its position and restores it after returning or after a refresh rebuilds the rows. When the row is gone, `restoreRowIndex(sectionId, position)` picks the row now at its position, or the last row above it; with no rows left, focus goes to the last shelf above, and only with no shelf at all to the hero. Up/Down move between these rows and Bloom's own shelves in visual order.
- **Tests**: `HomeRowsAndWatchlistTest` covers the model, the libraries it passes, when recommendations are read again (not on a favorite or watchlist change), dropping them (and the Watch Tonight row) at once, a late Watch Tonight row inserted in place, rows added and removed without a reset, the focus row after a refresh, the favorite-change refresh, and both detail pages' watchlist toggles; `SiloCatalogServiceTest` covers section filtering, the Watchlist row, the watchlist requests, and the Watch Tonight row (first, reused until a new Home, cold, empty, a late answer after the layout, a failed read keeping the row, a failed layout, both failing, the setting off, and with the production default on beside the Watchlist read and the `item_limit` 400/422 retries); `WorkspaceRoutingTest` covers the Jellyfin Favorites and recommendation rows, their settings, failed reads (a library's last categories), stale answers, hidden-library items, the 10.11 version gate and reuse until a reload; `HomeRecommendationsTest` covers the titles, the movie filter, merging, the caps, the version gate, identical "similar to" rows, the allowed items and the reuse lifetime; `ProviderCatalogTest` covers the recommendation, library membership and server info requests and parsing.

## WatchHistoryViewModel
The data behind `HistoryScreen.qml`: what the viewer watched on the live connection, most recent watch first. It is a creatable QML type (`WatchHistoryViewModel`, registered through `ui/WatchHistoryViewModelRegistration.h`), so each History page owns one.

- **Model**: list rows are canonical movie, series and episode maps (LibraryKinds: every other type is dropped), each title once across pages (an episode stands for its series, so a series shows once, at its newest watch), with roles `itemData`, `itemId`, `mediaType` and `name`; `count`, `get(row)` and `indexOfItem(itemId)` serve the grid and focus restore. Pages only insert rows (`rowsInserted`), so the focused card keeps its place; a new load resets.
- **Load**: `load(hiddenLibraryIds)` starts over on the live connection; the History page passes `Workspaces.hiddenLibraryIds` for it. `isLoading` covers the first page. Without a live connection it is an error and nothing is sent.
- **Silo** (one list): `LibraryService::getWatchHistory` reads `listHistory` by `page.next_cursor` in pages of `PageSize` (60). The server rolls an episode watch up into its series card and shows each title once. A page may be short or empty while the cursor says more remain, so a page that adds no card reads the next at once, up to `MaxEmptyPages` (5) in a row; then `hasMore` stays set and the page offers "Look further back" (`loadMore()`). A page that says more without a cursor ends paging.
- **Jellyfin** (`LibraryService::watchHistoryByLibrary`, `ProviderCapability::LibraryScopedHistory`): Jellyfin keeps no watch log, only each item's played state and `LastPlayedDate`, and `/Items` takes one `ParentId`. The model lists the connection's libraries (`getViewsForRequest`), keeps the movie and series ones the space does not hide, reads each library's played movies and episodes by `DatePlayed` (`getWatchHistory(libraryId, startIndex, …)`), and merges them with `CombinedLibraryCursor` sorted by `datePlayed` (`userState.lastPlayedAt`) descending. A card is released only when every library that still has items has one buffered, so the order never changes as pages arrive. Episodes of one series make one card, the newest watch (Silo shows series cards for the same reason); episodes already shown do not count toward the page, so the merge reads on, up to `MaxLibraryRounds` (5) rounds of library pages per page, then waits for `loadMore()`. A library whose page fails ends for that load; every library failing (or the library list failing) is an error. No supported library is an empty history.
- **Paging and errors**: `loadMore()` reads one page at a time while `hasMore`. The page asks for it as focus or the pointer nears the end, again after a page that added cards while focus is still near the end, on Down from the last row, and from the grid footer's "Look further back" (with a busy indicator), shown whenever cards are shown and more remain. A failed later page keeps the cards and `hasMore` and emits `pageFailed(message)` for a toast, so the next `loadMore()` tries again; a cursor the server rejects (a 4xx such as `invalid_cursor`) starts the list over from the top instead. After a failed or empty first read, the page's Try again or Look further back action takes focus. Every request has a key unique across instances; answers for another connection, key or an older load are ignored.
- **Actions**: `actionsFor(item)` lists `{id, text, enabled, navigation}`: Go to details (`openDetails`, movies and series) or Go to series (`openSeries`, episodes, disabled without `seriesId`), then, when `canRemove` (`LibraryService::supportsWatchHistoryRemoval`, `ProviderCapability::WatchHistoryRemoval`, Silo), Remove from history (`remove`) with `confirmTitle`, `confirmMessage` and `confirmText`: removal also counts the title as unwatched and drops its resume point, so the page asks first. `trigger("remove", item)` takes the card out at once (`rowsRemoved`) and sends `LibraryService::removeFromWatchHistory`, which answers through `homeCardWriteFinished` like the Home card writes. A refusal puts the card back where it was, before the first card that came after it, whatever else was removed or put back meanwhile, and emits `actionFailed(message)` for a toast. When the session changes before the server answers (`homeCardWriteUnconfirmed`), the removal may have landed: the card stays out, `actionFailed` says Bloom couldn't confirm it, and `needsReload` makes the page read the list again when it is shown next. A success emits `watchHistoryItemRemoved`, on which Home reads Continue Watching and Next Up again (the server also cleared watched state and resume points, a series' episodes included). One removal per card runs at a time, a reload while it runs keeps the card out, and a card of another connection, or any card once the session moved on, is refused. There is no undo: the server's removal is `non_retryable` and cannot be reversed.
- **Merged spaces**: the page reads the live connection only, the account Settings > About & Account names; it declares `ownerConnectionId`, so Back skips it once a route moves the session to another source. History is not merged across sources.
- **Tests**: `WatchHistoryViewModelTest` covers cursor paging and filtering, empty Silo pages, errors and retries, the Jellyfin library merge, hidden and unsupported libraries, failed libraries and views, the merge with libraries answering in either order, one card per series and the round limit, stale answers and two instances, optimistic removal with rollback, overlapping refusals restored in order in either reply order, an unconfirmed removal, later-page failures and a rejected cursor, refusing other connections' cards, and the actions per provider. `SiloCatalogServiceTest` and `ProviderCatalogTest` cover the provider requests and parsing; `CombinedLibraryTest` covers the `datePlayed` order.

## UpcomingViewModel
The data behind `UpcomingScreen.qml`: the episodes airing on the live connection from today through `WindowDays` (30) days later. It is a creatable QML type (`UpcomingViewModel`, registered through `ui/UpcomingViewModelRegistration.h`), so each Upcoming page owns one.

- **Model**: one list row per local day that has airings, in order, with roles `date` (`YYYY-MM-DD`), `title` ("Today", "Tomorrow", else the weekday and date, `dayTitle`) and `airings`: canonical calendar airings ([canonical models](canonical-models.md#ratings-and-airings)) with the page's labels added (`localDate`, `timeLabel`, `episodeLabel` such as "S2 E5" or "Season 3", `badgeLabel` such as "Season premiere" or "Finale", and `subtitle`, the three joined for the card). `count` is the number of days and `airingCount` the number of airings. `get`, `airingAt`, `indexOfDay` and `indexOfAiring` let the page find a card again by day and ID.
- **Days** (`groupByDay`): an airing with an instant (`airAt`) falls on its local day in the system zone, so day boundaries follow the zone's daylight-saving changes; one with only a day keeps `airDate`. Days before today and after the window are dropped (Jellyfin also lists yesterday's). Within a day, airings with a time come first by time (an instant on the viewer's clock, or Silo's `airTime`, the network's wall clock when its zone is unknown, which `timeLabel` shows as is), then the rest by series name, season and episode. A timer checks the local day just past midnight and at least every minute (a timer stands still while the machine sleeps, so after a suspend across midnight the next check catches it); a new day regroups, so "Today" moves on while the page is open, and reads again when the calendar is stale.
- **Load**: `load()` reads `LibraryService::getUpcomingAirings(filter, requestKey)` for the live connection; `isLoading` covers the read. Without a live connection it is an error and nothing is sent. A failure sets `hasError` and `errorMessage` (Try again calls `reload()`); a read of another preset or connection drops the shown days first, and a refresh of the same view keeps them until the answer; when that refresh fails the days stay and `refreshFailed` lets the page show a toast. Answers for another connection or an older request key are ignored, and `LibraryService` answers a read the session moved past as failed (`failStaleUpcomingReads`), so the page never waits on a dropped reply.
- **Presets**: `filters` lists Following (`following`, the default), Trending (`trending`) and All (`everything`). `filterable` follows the answer's `filterable` flag (Silo honors presets; Jellyfin does not), and the page shows the presets only then. Setting `filter` reads again. The preset chosen on a connection is remembered for the session (not saved), so the page opens on it on the next visit; Following until one is chosen.
- **Empty states**: an empty calendar is not an error. `emptyTitle` and `emptyMessage` follow the preset (on Jellyfin they name the TMDb plugin's "Create unaired (upcoming) episodes" option, which creates the episodes Jellyfin lists), and `emptyActionFilter` names the preset that shows more (`everything`) when there is one.
- **Freshness**: `refreshIfStale()` (the page calls it when shown again) reads again when the last read is older than `StaleAfterMs` (10 minutes, on the view model's clock; Silo's poster URLs expire) or the live connection changed, and otherwise regroups for the current day.
- **Merged spaces**: the page reads the live connection only; it declares `ownerConnectionId`, so Back skips it once a route moves the session to another source. The calendar is not merged across sources, and the page header names the source it lists (`MergedCatalog.sourceLabel`).
- **Tests**: `UpcomingViewModelTest` covers day grouping in local time across both daylight-saving transitions, the window edges, the order within a day, the labels and badges, day titles, presets and stale answers, empty states per provider, errors and a missing connection, refreshes (regrouping on a new day, fresh until 10 minutes on the injected clock, reading again for another connection), the day check firing at midnight and after a suspend, wall-clock times sorted with instants, and the preset remembered per connection. `SiloCatalogServiceTest` covers the Silo request, presets, the parse and projection, and a read answered as failed after a session change; `ProviderCatalogTest` covers the Jellyfin request, its OpenAPI parameters, an empty answer and the projection; `SiloCatalogServiceTest::jellyfinUpcomingProbesThenPagesTheCalendar` covers the Jellyfin probe, paging, the page cap and the chip's 30-day window.

## LibrarySectionsViewModel
The shelves a Silo profile curates for one library, which `LibraryScreen.qml` shows instead of the grid when the viewer picks Shelves (see [provider compatibility](provider-compatibility.md#catalog-and-conditional-requests)).

- **Model**: one list row per server row, in the server's order, with roles `sectionId`, `title`, `sectionType`, `featured`, `items` (canonical camelCase movie and series maps), `hasMore` and `loadingMore`; `count`, `libraryId` and `available` are properties. `LibraryService::getLibrarySections` picks the rows and maps the items.
- **Availability**: `available` follows `LibraryService::supportsLibrarySections` (`ProviderCapability::LibrarySections`, native Silo only). Without it `load` clears the model and sends nothing, so Jellyfin libraries never show the toggle.
- **Ownership**: `load(libraryId)` drops rows of another library or connection first; only the answer to the newest request for that library and connection is applied. A failure sets `hasError` and keeps the rows. `clear()` drops everything; the library list and combined pages call it, and so does a sign-out.
- **Updates**: a reload with the same row IDs in the same order updates rows in place (`dataChanged`); other changes reset the model. The grid's filters and search do not reload the shelves. `LibraryScreen` reads the rows once per library visit, which is enough to offer the toggle, and again on a return only while the shelves are shown.
- **Paging**: a row has more (`hasMore`) only when Bloom's `item_limit` cut it: `LibraryService` sent the cap, the row came back full at it, and `total_count` is larger. `total_count` alone counts the section's whole set, past its own limit, which `getLibrarySectionItems` does not exceed. `loadMore(row)` reads the whole row once, when focus nears the end of a row with `hasMore`. The answer replaces the row's cards and the row then has no more. A failure clears `hasMore` too, so focus moves do not repeat the read; the next load restores it. A reload that brings only the first page again keeps, after it, every card the row showed that the page lacks (by item ID), so focus returning to a card there finds it and a card the new page pushed out is not lost; the row keeps its `hasMore`, so its next read replaces the merge with the server's row.
- **Focus**: `LibraryScreen` saves the focused shelf and card as `{sectionId, itemId}` (with their positions as a fallback) and finds them after a reload with `rowOfSection` and `indexOfItem`; a shelf whose cards change keeps its focused card by ID.
- **Tests**: `LibrarySectionsViewModelTest` covers ownership, in-place updates, paging, the failure back-off, the merge by identity, lookup by ID and availability; `SiloCatalogServiceTest` covers the reads, the shared item cap and when a row has more; `ProviderCatalogTest` covers the requests and parsing.

## SubtitleSyncViewModel
"Sync to Audio" and "Reset Timing" for the selected external subtitle in the playback settings pop-out (`src/viewmodels/SubtitleSyncViewModel.*`, QML context property `SubtitleSync`; behaviour in [playback](playback.md#syncing-subtitles-to-the-audio)). It is a plain `QObject`, not a list model.

- **Properties**: `available` (the capability allows the selected subtitle's `syncKey`), `canReset` (the server holds a correction and nothing is under way), `busy`, `progress` (0..1) and `statusText`, the row's second line. `available` and `canReset` have their own change signals, so the pop-out rebuilds its rows only when they change, not on every poll; `stateChanged` covers the rest. `notice(message)` reports the end of a job the user started, or of a reset.
- **Actions**: `startSync()` starts a job or joins the active one; `resetTiming()` reads the validator and restores the identity timing; `cancel()` drops the requests in flight and stops polling.
- **Context**: it follows `PlayerController` (playback state, item, `mediaSourceId`, `playSessionId`, selected subtitle and track list) and `PlaybackService::subtitleSyncIdentity()` (connection, account and profile). The capability (`Bloom::SubtitleSyncCapability`: `available`, `autoSync`, `external`) is read at each playback start through `PlaybackService::loadSubtitleSyncStatus` and belongs to that identity; a failed read is asked again on the next subtitle or playback. Selecting a syncable subtitle reads its state once, which also records the timing mpv has loaded. Stopping, another item or session, or another subtitle cancels the request and the polling and forgets the state.
- **Requests**: one action request at a time, each under its own key; answers to an older key, or for another subtitle, are dropped, and nothing waits on them. `PlaybackService::subtitleSyncIdentityChanged` (an account, profile or session change, after which the transport may drop requests silently) makes it send the request again for the same identity, or stop following the job for another.
- **Reload and delay**: when an answer carries a timing other than the one mpv has loaded, it calls `PlayerController::reloadSelectedExternalSubtitle()` and waits for `externalSubtitleReloadFinished` before it reports the outcome. A loaded `synced` timing sets the subtitle's delay override to 0 (`PlayerController::setSubtitleDelayOverride`); a loaded original timing clears it. A deferred reload (buffering) runs on the next playback state change; a failed one is tried again on the next read.
- **Automatic sync**: with `autoSync`, a subtitle first read with its own timing and no job is read once more `kAutoSyncRecheckMs` after mpv loads it (`PlayerController::externalSubtitleLoaded`).
- **Tests**: `SubtitleSyncTest` covers the service's Silo requests over a fake network (paths, profile header, the `ETag`, replay of the coalescing start, `If-Match` and the reset body, refusal of keys outside the pattern, cancelled answers dropped) and the view model with a real `PlayerController`: poll, finish, `sub-add … select` with `sub-remove` only after the new sid, the override persisted in the season scope while the season delay stays, nudging the override, other subtitles keeping the season delay; a `sid=no` and the old sid during a reload; a reload mpv never reports (old copy kept, late copy removed, retried on the next read); a reload deferred while buffering; a timing change across a seek re-anchor; the HLS offset applied once after the reload; the poll cap and a later sync judged by the timing; the automatic-sync re-read; the `external` flag and a `404` hiding the row; identity changes re-sending or settling requests; a refused start and a failed job leaving the subtitle and the delay alone; `no_match`; cancellation on stop and on another subtitle; one capability read per playback; reset and a refused replay settled by a read; and no offer without the capability or on an embedded track. `TrackPreferencesManagerTest` covers the override round trip and its bound. `SiloPlaybackProviderTest` covers the `sync_key` mapping, the capability's `auto_sync` and `external`, the request builders and their retry safety, and state parsing.

## Continue Watching and Next Up
Home's two first shelves come from one list, `LibraryService::canonicalNextUpLoaded` (or `MergedCatalog.nextUpLoaded` in merged spaces). The order is decided in C++: for providers with a resume list (Jellyfin), `ContinueWatching::combine` (`src/models/ContinueWatching.*`, `Bloom::Models`) puts each item once (an episode in both lists keeps its resume copy), in-progress items first by last played, then Next Up in its order; Silo's list keeps the server's order. Only the newest refresh publishes; an older one that answers later is dropped. `ContinueWatchingTest` covers the ordering; `WorkspaceRoutingTest` covers the single and merged reads and stale refreshes.

### ContinueWatchingViewModel
`ContinueWatchingViewModel` (`src/viewmodels/ContinueWatchingViewModel.*`) holds that list for one Home. It is a creatable QML type (registered through `ui/ContinueWatchingViewModelRegistration.h`), so a new Home (sign-in, space switch) starts empty.

- **Rows**: `setItems(list)` takes each published list. `continueWatching` holds the cards with a `positionMs`, `nextUp` the others, or every card when `mergeRows` (bound to `mergeContinueWatchingWithNextUp`) is on. `items` is every shown card for the hero and backdrops. All three change together with `itemsChanged`. The shelves' ListViews use `continueWatchingModel` and `nextUpModel` (`HomeCardListModel`, role `modelData`, `count`, `get(i)`), which apply each change as row inserts, removes, moves and data changes keyed by connection and item, so the focused card keeps its place. Home restores focus with `Qt.callLater` only when nothing on Home holds it.
- **Actions**: `actionsFor(item)` lists a card's actions in menu order, each `{id, text, enabled, navigation}`, from the capabilities of the card's own connection (`LibraryService::homeCardCapabilities`, which reads the provider of a merged member that is not live):

  | Action | Shown for | Write |
  | --- | --- | --- |
  | Go to series (`openSeries`) / Go to details (`openDetails`) | episodes / movies | none; QML navigates (disabled without `seriesId`) |
  | Remove from Continue Watching (`remove`) | cards with a position | Silo: dismissal on `continue_watching`, disabled without `progressUpdatedAt`; Jellyfin: resume position set to zero |
  | Hide from Up Next (`hide`) | Silo cards without a position | dismissal on `next_up`, disabled without `seriesId` |
  | Stop watching ‹series› (`remove` / `hide`) | Silo episodes on either row | the same dismissal; it drops the whole show, also on the profile's watch services (Trakt), so the action carries `confirmTitle`, `confirmMessage` and `confirmText` and Home asks first |
  | Mark as watched / unwatched | every card, by `watched` | `setHomeItemState(key, "watched", …)` |
  | Add to / Remove from favorites | movies | `setHomeItemState(key, "favorite", …)` |
  | Add to / Remove from watchlist | movies, providers with a watchlist | `setHomeItemState(key, "inWatchlist", …)` |
  | Not interested / Interested again | movies, when the live profile allows it (`supportsNotInterested`) | `setHomeItemState(key, "notInterested", …)` |

  Jellyfin has no Next Up hide; its Up Next cards offer Mark as watched instead. Favorite and watchlist are left off episode cards because a card carries the episode's state, not the series'; the series page has both.
- **Running an action**: `trigger(id, item)` runs a non-navigation action on the live connection. QML routes a merged card to its owner through `SourceRouter` first; a card of another connection is refused with `actionFailed`. One write per card runs at a time. Removals and Mark as watched are optimistic: the card leaves its shelf at once. A Silo episode dismissal drops the show, so every card of that series leaves both rows; Jellyfin's resume reset hides only the Continue Watching card, since the episode may come back as an Up Next card. Favorite, watchlist and Mark as unwatched change the card's field in place.
- **Outcome**: every write carries a request key, and `LibraryService::homeCardWriteFinished(connectionId, key, …)` answers it once; a reply settles only the card with that key and connection. A refusal puts the card (or field) back and emits `actionFailed(message)` for a toast. When the session changes before the server answers (a route, a profile or account switch, sign-out), LibraryService answers the write as failed at once, since its reply would be dropped; a reply that still lands is ignored. A confirmed removal stays hidden until the next list and emits `refreshRequested`; Home then reads Next Up again, and that newer read supersedes any read still in flight. Field changes in flight are kept over lists read before they land.
- **Undo**: a confirmed Silo dismissal emits `undoOffered(message)`, sets `undoAvailable` and `undoConnectionId`, and Home shows a toast with Undo. `undo()` shows the cards again at their former places, even when a newer list already left them out, and sends the undismiss; until it is answered, lists read before it keep those cards shown, and a refusal hides them again. A newer dismissal replaces the undo, and `dismissUndo()` drops it when the toast closes. Home keeps the undo while its own route is pending, and a failed route clears it with a toast. Jellyfin removals and Mark as watched have no undo.
- **Tests**: `ContinueWatchingViewModelTest` covers the split, row changes without resets, the actions per provider and card, the episode confirmation, optimistic removal and rollback, the hidden show, undo and its failure, undo over a stale list, an expired undo, field toggles and their survival across a refresh, account-scoped replies, a late reply after a failure, and refusing another connection's card. `SiloCatalogServiceTest::homeCardWriteAnswersWhenTheSessionChanges` covers the failure LibraryService reports for a write whose session went away. `WorkspaceRoutingTest` (`homeCardWritesReachTheOwningMember`) runs a merged space: each card's write reaches its owner's server with that member's credentials after routing. `SiloCatalogServiceTest` and `ProviderCatalogTest` cover the provider requests.

## User ratings
`UserRatingState` (`src/viewmodels/UserRatingState.*`) is the viewer's own rating of one movie or series. `MovieDetailsViewModel::userRating`, `SeriesDetailsViewModel::userRating` and `UpNextRecommendationsViewModel::movieRating` each own one; QML binds `UserRatingControl` to it.

- **Scale**: `scale` comes from `LibraryService::userRatingScale()`: `stars` (1 to 5) on Silo, `likes` (1 like, -1 dislike) on Jellyfin, empty otherwise. Silo has no capability document for personal ratings (`getRatingsCapability` describes the external rating sources), so stars show on every Silo connection; a write refused with 503 (Silo without its ratings service), 501, 404 or 405 hides the control for that connection and profile until restart, and `userRatingSupportChanged` re-reads `scale`. `supported` is false with an empty scale or no item, and the control is hidden.
- **Value**: `value` is the canonical `userRating` (stars) or `userLikes` (likes) of the item, 0 when unrated. `updateFromItem` takes it from each canonical detail map unless a change is in flight.
- **Rating**: `rate(value)` changes `value` at once and sends `LibraryService::setUserRating`; rating the current value sends 0 and clears it. Values outside the scale are ignored, and so are presses while `pending`. A refusal (`userRatingFailed` for this connection, item and value) puts the earlier value back and emits `updateFailed(message)` for a toast. `userRatingChanged` for the connection and item settles it, including a rating set for the same item on another page, and emits `confirmed`; the detail view models then write it into their details cache. When the session changes before the server answers (a route, a profile or account switch, sign-out), LibraryService fails the write at once, so the control never stays pending.
- **Control**: `UserRatingControl` keeps its buttons enabled while a change is pending (they dim instead), so focus stays on the pressed star or thumb; the state ignores the presses.
- **Routing**: `setItem(itemId, connectionId)` binds the state to the item's connection (the live one when empty); answers and details from another connection are ignored, and `rate` sends nothing while another connection is live. `UserRatingControl` runs each rating through `SourceRouter` to `connectionId` first, and the after-movie screen routes its reads to the movie's `connectionId` the same way. Detail pages open on the owning member already.
- **Tests**: `HomeRowsAndWatchlistTest` covers details that arrive before the scale, optimistic changes, ignored presses in flight, rollback, clearing, out-of-scale values, other items' and other connections' answers, no write while another connection is live, and the details cache, for stars (movie) and likes (series). `SiloCatalogServiceTest` covers the provider requests, never replaying a failed write, hiding stars after a 503, a write failing when the session changes (`staleRatingWriteFailsAfterSessionChange`), and the Jellyfin like routes. `UserRatingControlTest` checks that focus stays on the rated button while the write is pending.

## Up Next and after-movie rows
`UpNextRecommendationsViewModel` feeds `UpNextScreen.qml` and `AfterMovieScreen.qml`; one screen uses it at a time and clears it when it leaves.

- **Episodes**: `loadUpcomingEpisodes(seasonId, startEpisodeId)` lists the queued episode and the rest of its season (`upcomingEpisodes`). Without a next episode, `loadForSeries(seriesId)` lists up to six series in `items`: library similar items first, then request discovery results (Seerr or Silo) when the series has a TMDB id.
- **Movies**: `loadForMovie(movieId, limit = 12)` reads `LibraryService::getBecauseWatchedItems` (Silo `listBecauseWatched`, else Jellyfin similar items) into `items`, keeping movies and series only (`selectBecauseWatched` drops other types, the movie itself, and repeats of the same connection, type and item id; a movie and a series that share a TMDB number, or two titles with one name, both stay). It also reads the movie's details fresh (`getItem` with its own request context, after clearing cache validation) into `movie`, and sets `movieRating` to the movie. Similar items read for the movie's own details page are not this answer.
- **Failures**: provider failures are silent: `items` stays empty and `loading` ends. Answers for another connection, another source item, or an older load are ignored.
- **Tests**: `UpNextRecommendationsViewModelTest` covers the series merge, upcoming episodes, stale answers, the because-watched filter, the movie load (requests, details, rating), silent failures, and switching back to a series. `SiloCatalogServiceTest` covers the because-watched request and the Jellyfin fallback.

## PersonViewModel
The data behind `PersonScreen.qml`: one person and the movies and series they appear in on the live connection. It is a creatable QML type (`PersonViewModel`, registered through `ui/PersonViewModelRegistration.h`), so each person page owns one and stacked person pages keep their own state.

- **Load**: `load(person)` takes the canonical person map a cast card or a people search result carries. Its name and photo show at once; a credit's `role` and `kind` are dropped. The page then reads `LibraryService::getPerson` and the first page of `getPersonItems` on the live connection. A person whose `connectionId` is another source's is refused with an error (merged spaces route to the owning connection before the page opens).
- **Properties**: `person` (the seed, replaced key by key by the read; a seed photo stays when the read has none), `personId`, `connectionId`, `movies`, `series`, `hasMore`, `loadingMore`. The list rows are the filmography in server order, with roles `itemData`, `itemId`, `mediaType` and `name`. `movies` and `series` are one `PersonTitlesModel` per shelf (same roles, a `count` property and `get(row)`).
- **Filtering**: only `Movie` and `Series` items are kept (LibraryKinds), each item ID once across pages.
- **Paging**: pages of 60. `loadMore()` reads the next page while `hasMore`, one at a time, continuing from the server's cursor (Silo) or the number of items the server has sent, before filtering (Jellyfin). New titles are appended (`rowsInserted`) to the list and to their shelf's model; neither is reset until the next load, so a shelf keeps its focused card and scroll position while more titles arrive. An empty page ends paging.
- **Loading and errors**: `isLoading` covers the details and the first page. A failed first page sets `hasError`/`errorMessage`; failed details keep the seed with no error; a failed later page keeps the titles and `hasMore`, so the next `loadMore()` tries again. `reload()` starts over.
- **Ownership**: each page request has its own request key, unique across every `PersonViewModel` (two pages may show the same person); answers for another connection, person or an older load are ignored.
- **Tests**: `PersonViewModelTest` covers loading, the seed, filtering and de-duplication, paging by count and cursor, errors and retries, stale answers, refusing another source's person, shelves that only grow by inserts, and request keys of two instances. `ProviderCatalogTest` and `SiloCatalogServiceTest` cover the provider requests and mapping.


## SubtitleSearchViewModel
Online subtitle search for the playing file, behind the "Search subtitles…" page of the playback settings pop-out (see [playback](playback.md#searching-for-subtitles)). It is app-wide (`SubtitleSearch` in QML, registered by `ApplicationInitializer` after the other view models) and reads `PlaybackService`, `PlayerController` and `ConfigManager`.

- **Model**: one row per result, best first (`Bloom::sortSubtitleSearchResults`: file match, score, downloads), role `result` with the canonical `SubtitleSearchResult` map. `results` holds the same maps for the overlay's row list; `count` and `searched` tell an empty answer from no search yet, and `warnings` lists providers that failed while others answered (Silo).
- **Availability**: `available` is true while an item plays on a connection whose provider offers the search (`PlaybackService::loadSubtitleSearchStatus`). The answer is kept per connection and profile (`PlaybackService::subtitleSearchScope`), so the status is read once, and again after `subtitleSearchScopeChanged` (a profile, account or rights change); a failed read is not kept.
- **Language**: `languages` is `ConfigManager.supportedTrackLanguages`; `language`/`languageLabel` start at the subtitle language setting, else the audio language, else English, until the user picks one. `setLanguage` searches again at once; `cycleLanguage(step)` shows the new language loading and searches once it has stayed for `kLanguageSearchDelayMs` (500 ms).
- **Flow**: `open()` searches unless results for this item and language are shown or loading. `search()`/`reload()` search again; `isLoading`, `hasError` and `errorMessage` follow the search. `download(resultId)` runs one download at a time (`downloading`, `downloadingId`) and remembers the selected subtitle. Once the server answers it calls `PlayerController::addDownloadedSubtitleTrack`: with the same subtitle still selected, the download is selected and `downloading` stays true until the player reports it loaded (`downloadedSubtitleLoaded`, then `subtitleLoaded(title)`) or failed (`downloadFailed(message)`); when the viewer picked another subtitle meanwhile, it is only listed (`subtitleListed(title)`). A stream change under the same item while a download is in flight drops it with `downloadFailed`.
- **Ownership**: the state belongs to one playing item (connection, item, media version and session). Each request has its own key that includes a generation; answers for another key are dropped, so a search replaced by another language, a download whose item stopped playing, or any answer after playback stops is ignored. Playback stopping or moving to another item cancels the requests in flight and clears the results; `cancel()` drops them too.
- **Tests**: `SubtitleSearchTest` covers the flow from search to the pick saved after mpv's confirmation, a failed load, a manual pick during the download, stale answers, cancellation when playback stops, the interrupted-download notice, gating per profile, warnings, the debounced language steps and the default language, alongside the provider requests and `PlaybackService` flows.

## Collection view models
Collections are a browse view over a library's movies and series ([canonical collections](canonical-models.md#collections)). Three creatable QML types (registered through `ui/CollectionViewModelRegistration.h`) hold them, all in `src/viewmodels/CollectionViewModels.*`, so each page owns its own state.

- **`LibraryCollectionsViewModel`**: the collections of one library, for `LibraryScreen`'s Collections view. Roles `collectionData`, `collectionId`, `name`; properties `libraryId`, `connectionId`, `available` (`LibraryService::supportsCollections`, `ProviderCapability::Collections`), `loaded`, `count`, `hasMore`, `loadingMore`, `serverWide` (the list is the server's, not only the library's; see `LibraryService::getLibraryCollections`). `load(libraryId)` reads the first page (100) unless that library on the live connection is already loaded or loading; without the capability it sends nothing. `refreshIfStale()`, also run by `load` of the shown library, reads the loaded collections again once they are older than 10 minutes (`StaleAfterMs`), page by page until every row is refreshed, and replaces each row in place (`dataChanged`, no reset or insert), so Silo's signed artwork URLs are renewed without moving focus; a failed refresh keeps the rows. Pages continue from the number of collections the server sent (Jellyfin; Silo answers the whole tab) and only insert rows. A failed first page sets `hasError`; a failed later page keeps the rows and `hasMore`. Collections without an ID, a connection or a kind are dropped, each ID once. `get(row)` and `indexOfCollection(id)` serve the grid; `clear()` drops everything.
- **`CollectionViewModel`**: one collection's titles, for `CollectionScreen`. `load(collection)` takes the canonical collection map and refuses one whose `connectionId` is not the live connection (merged spaces route first) or that is not a collection. Rows are canonical movie and series maps only (LibraryKinds), each ID once, with roles `itemData`, `itemId`, `mediaType`, `name`. `sortBy` (`""` for the collection's own order, `releaseDate`, `title`; `sorts` lists them) reads the collection again from the first page; another value is refused. Pages of 100 continue from the server's cursor (Silo) or the count it sent before filtering (Jellyfin) and only insert rows. `totalCount` is the server's count less the titles Bloom dropped while pages remain, then the loaded count. Errors work as in `LibraryCollectionsViewModel`.
- **`ItemCollectionsViewModel`**: the collections that hold one title, for the movie and series pages' "Part of" shelf. `load(itemId)` reads `LibraryService::getItemCollections`; the same title keeps its collections shown until the answer replaces them, another title (or connection) clears them first. A failed or unsupported read shows nothing and reports no error. Properties `itemId`, `connectionId`, `collections`, `count`, `loading`.
- **Ownership**: every request has a key unique across every instance; answers for another library, collection, title, connection, sort or an older load are ignored.
- **Tests**: `CollectionViewModelsTest` (linking `Bloom::Network`) covers the capability gate, loading once per library and connection, the server-wide flag, stale refreshes in place, filtering and de-duplication, paging by count and cursor with inserts only, first- and later-page failures and retries, stale answers, sort changes dropping answers of the old order, refusing another source's collection, and the "Part of" model's reloads, failures and stale answers. `ProviderCatalogTest` covers the requests (Jellyfin ones against the pinned OpenAPI manifest), parsing and mapping of both providers; `SiloCatalogServiceTest` covers the reads through `LibraryService`: Silo's (a `404` for one title stops nothing, a `422` stops "Part of"), Jellyfin 10.11's library scan (paging, box set reads by ID, the kept result, the server-wide fallbacks, no "Part of" request) and Jellyfin 12's scoped query and "Part of" after a `404`.
